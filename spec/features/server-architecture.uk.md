# Фіча: Архітектура сервера та розділення клієнт/сервер (v1.1)

Статус: **дизайн** (v1.1 — *Tick-server: рушій = WS/HTTP сервер, клієнти під'єднуються*).
Супутні: [ROADMAP §1.1](../ROADMAP.md), [ARCHITECTURE.md](../ARCHITECTURE.md). Англійський
оригінал: [server-architecture.en.md](server-architecture.en.md).

## 1. Навіщо сервер

Рушій — це **завжди-активний дешевий tick-loop**: більшість тіків це безкоштовний локальний стан
(дрейф потреб), модель викликається рідко, а цикл живе між ходами — саме це дозволяє агенту
самоініціюватись. Сьогодні цей цикл працює **в межах процесу**: TUI запускає `engine.run()` на
фоновому потоці й спілкується з ним через in-memory `Bridge`.

v1.1 виносить цикл у **окремий серверний процес**. Клієнти (зараз TUI, у v2 — веб) **під'єднуються
через WebSocket**; агент далі живе **без жодного під'єднаного клієнта**. Це фундамент мульти-агентного
**хабу** — один сервер хостить кількох агентів, кожен адресується своїм `agent_id`.

Головне усвідомлення з v0: **рушій ніколи не залежить від інтерфейсу.** Він уже спілкується зі світом
через два вузькі шви — `Channel` (вхід) і `Output` (події рендеру) — а TUI вже довів топологію
«потік + шина» (`Bridge`). Тож v1.1 — це **не** переписування розуму; це **мережева реалізація шини,
яка вже існує**, з `engine.run()`, якого **не торкаємось**.

## 2. Що вже зробив v0 (і що v1.1 перевикористовує)

| Шов v0 | Що це | Роль у v1.1 |
|---|---|---|
| `Channel.poll() -> str \| None` | неблокуючий порт вводу (`StdinChannel`, `ScriptedChannel`, `TuiChannel`) | `ServerChannel` вичитує чергу вводу агента, яку наповнюють WS-події `user.message`/`command` |
| `Output` (`user`/`agent`/`usage`/`notice`/`status`) | ядро пише **кожну** відповідь/usage/notice/status через цей порт, ніколи не `print` | `ServerOutput` серіалізує кожен виклик у WS-подію і **розсилає** її всім клієнтам цього агента |
| `Bridge` (echo-free inbox/outbox) | внутрішньопроцесні потокобезпечні черги між потоком рушія та UI | узагальнюється у **мережеву шину**: WS замінює in-memory черги; echo-free збережено |
| `status(snapshot)` щотіку | `{status, model, branch, tick, needs, thresholds, actions, hottest, cooldowns, stats}` | стає WS-подією `status` дослівно (живить статус-бар / панель потреб будь-якого клієнта) |
| `agent(text, is_self, lead, model, is_thought, is_curiosity)` | прапорці відповіді, що зросли у v0.10/v0.11 | подія `agnika.message` несе ті самі прапорці, щоб кожен клієнт рендерив однаково |
| `.kiln/store.json`, `state/*` | посесійний store + поагентна калібрація (`needs_model.yaml`, `mood.json`, `canon.md`, …) | масштабовано **по `agent_id`**, щоб агенти не ділили стан |

Оскільки контракт уже окреслено, **ядро рушія (`run`, `respond`, мізки, потреби) у v1.1 змінюється на
нуль рядків**. Увесь новий код — це хост + транспорт.

## 3. Модель процесу та конкурентності

```
                          ┌────────────────────────── серверний процес (один) ─────────────────────────┐
                          │                                                                            │
   ws://…/agent/agnika ───┤  AgentHost (реєстр: agent_id -> AgentRuntime)                              │
   ws://…/agent/pashu  ───┤                                                                            │
                          │   AgentRuntime("agnika"):                                                  │
                          │     ├─ engine.run(channel=ServerChannel, output=ServerOutput,              │
                          │     │             brain=LiveBrain)   ← на ВЛАСНОМУ потоці (як у TUI)        │
                          │     ├─ черга inbox   (WS -> рушій)                                          │
                          │     └─ outbox-хаб    (рушій -> всі підписані WS-клієнти)                    │
                          │                                                                            │
                          │   async-шар (FastAPI/Starlette + websockets):                              │
                          │     • приймає WS-з'єднання, маршрутизує по agent_id                         │
                          │     • качає inbox <- клієнт, outbox -> клієнти                              │
                          │     • HTTP: health, список агентів, вибірка історії                         │
                          └────────────────────────────────────────────────────────────────────────────┘
        ▲                                   ▲
        │ WS (JSON-події)                   │ WS (JSON-події)
 ┌──────┴───────┐                    ┌──────┴───────┐
 │ TUI-клієнт   │                    │ TUI-клієнт #2│   (веб-клієнт = v2)
 │ (render.py)  │                    │ (read-along) │   тонкий: рендер + ввід, жодної логіки агента
 └──────────────┘                    └──────────────┘
```

- **Один серверний процес.** Кожен хостований агент — це `AgentRuntime` з ключем `agent_id`, що тримає
  власний `engine.run()`, `State`, store і шину. v1.1 постачає **одного** агента (`agnika`), але хост,
  маршрути й шляхи персистенції масштабовані по `agent_id` **з першого дня**, тож додавання агентів у
  v2 — адитивне (без перебудови).
- **Tick-loop працює на сервері, незалежно від клієнтів.** Він стартує разом із сервером і тікає
  вічно — агент старіє, дрейфує і самоініціюється незалежно від того, чи хтось під'єднаний.
- **Блокуючі виклики моделі не морозять сервер.** Мізки v0 синхронні (`chat` через SDK, `deep`/`tool`
  через `claude -p`). v1.1 зберігає **перевірений патерн TUI**: запускає `run()` кожного агента на
  **окремому потоці**, тож блокуючий виклик блокує лише потік того агента — async-цикл (прийом
  з'єднань, прокачування подій інших агентів) лишається чуйним. Повноцінний чергово-подієвий **FSM**,
  що робить це явним, — це **v1.2**; v1.1 потрібен лише потік + неблокуючий транспорт.

## 4. Клієнт ↔ сервер: хто чим володіє

Розподіл суворий — і в цьому весь сенс дизайну.

| Зона | **Сервер** (розум агента + хост) | **Клієнт** (TUI / веб) |
|---|---|---|
| Потреби, дрейф, satiation, настрій, думки, цікавість | ✅ володіє | ❌ |
| Два мізки + cost-маршрутизація + самотригери | ✅ володіє | ❌ |
| Персистенція (store, ledger, транскрипти, стан) | ✅ володіє | ❌ |
| Виклики моделі + API-ключі + `claude -p` | ✅ володіє (ключі ніколи не залишають сервер) | ❌ |
| Tick-loop (живе без клієнта) | ✅ володіє | ❌ |
| Рендер відповідей / статусу / панелі потреб | ❌ | ✅ володіє |
| Захоплення вводу + слеш-команди | ❌ | ✅ володіє (пересилає як події) |
| Стан перегляду на з'єднання (скрол, копіювання) | ❌ | ✅ володіє |
| Будь-який стан агента | ❌ (без стану щодо агента) | ❌ |

**Клієнт — це тонкий термінал поверх потоку подій.** Він не тримає логіки агента; під'єднується,
підписується на один `agent_id`, рендерить отримані події й пересилає те, що вводить користувач. Два
клієнти на одному агенті бачать **ту саму сесію** (другий клієнт — read-along вид того самого живого
стану). Рушій **ніколи не імпортує клієнта**; клієнт **ніколи не імпортує рушій** — вони зустрічаються
лише на **протоколі подій**.

## 5. Мережева шина (Bridge → WebSocket)

In-process `Bridge` уже розділяє два потоки; сервер зберігає розділення, міняючи транспорт:

- **Inbox (клієнт → рушій).** WS-подія `user.message`/`command` кладеться в чергу вводу агента.
  `ServerChannel.poll()` її вичитує — контракт ідентичний `TuiChannel`. Рушій не знає, що це прийшло
  через сокет.
- **Outbox (рушій → клієнти).** `ServerOutput.agent(...)` (і `usage`/`notice`/`status`) серіалізує в
  JSON-подію й віддає **broadcast-хабу** агента, який роздає її **кожному** WS-клієнту, підписаному на
  цього агента. `ServerOutput.user()` лишається **no-op** (echo-free): клієнт сам показує введений
  рядок, сервер ніколи не повертає його назад — точно як зараз робить TUI-bridge.

Тож «кілька клієнтів бачать ту саму сесію» виходить безкоштовно: усі підписані на один хаб.

## 6. Протокол подій (контракт клієнт/сервер)

JSON-повідомлення поверх WS, що дзеркалять шви `Output`/`Channel` і наявні типи подій `Bridge`.

**Клієнт → Сервер**

| подія | пейлоад | значення |
|---|---|---|
| `attach` | `{agent_id}` | підписати це з'єднання на агента (також задається шляхом URL) |
| `user.message` | `{text}` | хід від користувача |
| `command` | `{text}` | слеш-команда (`/status`, `/mood`, …) — обробляється на боці рушія до маршрутизації |

**Сервер → Клієнт** (broadcast усім підписникам агента)

| подія | пейлоад | джерело |
|---|---|---|
| `agnika.message` | `{text, is_self, lead, model, is_thought, is_curiosity}` | `Output.agent` |
| `usage` | `{usage, latency}` | `Output.usage` |
| `notice` | `{text}` | `Output.notice` (вивід команд, `[exit]`, …) |
| `status` | `{snapshot}` (потіковий знімок, §2) | `Output.status` |
| `snapshot` | `{status, recent_history[]}` | надсилається **раз при attach**, щоб пізній клієнт наздогнав |
| `tick` | `{tick}` | опційний heartbeat (показати «живість» навіть у простої) |

**HTTP** (без стрімінгу): `GET /health`, `GET /agents` (список `agent_id` + статус),
`GET /agent/{id}/history?limit=N` (вибірка транскрипту для скролу при attach).

Протокол **адитивний над типами `Bridge`** — наявний `_render(event)` у TUI вже розуміє
`agent`/`usage`/`notice`/`status`; віддалений клієнт перевикористовує його майже дослівно.

## 7. Життєвий цикл з'єднання

1. **Attach** — клієнт відкриває `ws://…/agent/{agent_id}` (або шле `attach`). Сервер реєструє
   з'єднання на хабі цього агента.
2. **Наздоганяння** — сервер шле одноразовий `snapshot` (поточний `status` + останні N рядків
   транскрипту), щоб клієнт, який зайшов посеред сесії, одразу був консистентний.
3. **Live** — клієнт отримує broadcast-події й шле `user.message`/`command`.
4. **Disconnect** — з'єднання обривається; **агент далі живе** (тікає, дрейфує, може самоініціюватись).
   Ніщо в агенті не прив'язане до клієнта.
5. **Reconnect** — повторний attach → свіжий `snapshot` → продовження. Самоініційовані повідомлення,
   видані під час відключення, є в транскрипті й приходять у наздоганянні.

## 8. Масштабування по `agent_id` (мульти-агент з першого дня)

Хоча v1.1 хостить одного агента, **усе ключується по `agent_id`**, щоб хаб v2 був адитивним, а не
перебудовою:

- **Маршрути:** `ws://…/agent/{agent_id}`, `GET /agent/{agent_id}/…`.
- **Персистенція:** поагентні шляхи — `.kiln/{agent_id}/store.json`,
  `.kiln/{agent_id}/usage-ledger.jsonl` і поагентний `state/` (власні `needs.json`, `needs_model.yaml`,
  `mood.json`, `canon.md`, `prompts.md`). Дефолтний агент (`agnika`) мапиться на сьогоднішні шляхи для
  чистої міграції.
- **Рантайм:** один `AgentRuntime` на id (власний цикл, шина, мізок). Хост — це просто `dict`.
- **Permission scope** (поле, що згодом гейтить інструменти) тут чіпляється до кожного агента, але
  **ще не енфорситься** — енфорсмент це v1.3 (Tools). Проєктування поля зараз робить v1.3 адитивним.

## 9. Обсяг v1.1 (переглянуто з огляду на v0)

Оскільки v0 завершив шви, v1.1 щільно обмежений.

**У межах**
- Async-сервер (FastAPI/Starlette + websockets); `GET /health` + `GET /agents`.
- `AgentHost` + `AgentRuntime`, маршрути й шляхи персистенції по `agent_id`.
- **Два агенти хостяться одночасно — Агніка *і* компаньйон Pashu (§12)** — кожен окремий
  `AgentRuntime` із власним потоком, шиною, `state/{agent_id}/` і `.kiln/{agent_id}/` (розробка даних
  Pashu + під'єднання клієнта до нього — частина ЦІЄЇ версії, а не пізнішої).
- `ServerChannel` + `ServerOutput` + поагентний broadcast-хаб (мережевий `Bridge`).
- WS **протокол подій** (серіалізація наявних подій `Output`/`status`; echo-free).
- Tick-loop працює на сервері **без клієнта**; **неблокуючі** виклики моделі (потік на агента).
- **Remote-режим TUI-клієнта**, що під'єднується через WS до обраного `agent_id` і перевикористовує
  `tui/render.py` (in-process `Bridge` лишається для локалу/розробки).
- Тести проти `MockBrain`: сервер тікає без клієнта; клієнт під'єднується й тримає хід; **другий клієнт
  бачить ту саму сесію**; **Агніка і Pashu тікають одночасно з ізольованим станом**; нуль платних
  викликів.

**Поза межами (пізніші фази)**
- Явний чергово-подієвий **FSM** і стани `idle/thinking/responding/cooling` → **v1.2**.
- Реєстр **інструментів** з типізованими аргументами + поагентний **енфорсмент** дозволів → **v1.3**.
- **RAG**-пригадування по транскриптах → **v1.4**.
- **Веб**-клієнт і операторський **мульти-агентний** UI керування (додати/старт/стоп/інспект агентів з
  панелі — v1.1 реєструє Агніку + Pashu в конфізі) → **v2**.
- Auth / TLS / багатокористувацькі акаунти (для v1.x припускаємо одного оператора на localhost).

## 10. План реалізації

Упорядковано, кожен крок постачабельний і покритий тестами; пізніші залежать від ранніх.

1. **Каркас сервера.** Додати пакет `server/`: застосунок FastAPI/Starlette, `GET /health`, заглушку
   WS-ендпоінта, що приймає з'єднання й шле `notice`. Додати `fastapi`/`uvicorn`/`websockets` у
   залежності (опційний extra `[server]`, як `[tui]`). *DoD: `uvicorn server:app` працює; WS-клієнт
   під'єднується й отримує `notice`.*
2. **Мережева шина.** `ServerChannel(inbox_queue)` + `ServerOutput(hub)`, що реалізують протоколи
   `Channel`/`Output` з v0; `BroadcastHub` (subscribe/unsubscribe/broadcast, потокобезпечний).
   Контрактні тести закріплюють їх під ті самі очікування, що `TuiChannel`/`TuiOutput`. *DoD: фейковий
   рушій крутить хаб; події віялом ідуть двом підписникам; `user()` — no-op.*
3. **AgentRuntime + AgentHost.** `AgentRuntime(agent_id)` стартує `engine.run(channel=ServerChannel,
   output=ServerOutput, brain=LiveBrain)` на потоці; `AgentHost` — реєстр `agent_id -> runtime`.
   Поагентні шляхи стану/стору (`.kiln/{agent_id}/…`). *DoD: хост стартує одного агента; він тікає без
   клієнта (статус-події течуть у хаб).*
4. **WS-протокол + життєвий цикл.** Підключити WS-ендпоінт: на attach слати `snapshot`; качати
   `user.message`/`command` → inbox; стрімити події хаба → клієнт; обробляти disconnect (агент живе
   далі). Визначити типізовані (де)серіалізатори подій. *DoD: тестовий WS-клієнт під'єднується, шле
   повідомлення, отримує `agnika.message` + `usage`; другий клієнт отримує те саме; disconnect не
   спиняє тіки.*
5. **Неблокуючість під навантаженням.** Перевірити, що блокуючий `deep` на потоці одного агента не
   стопорить async-шар (другий агент / запит `/health` лишаються чуйними). Винести будь-яке випадкове
   блокування loop-потоку. *DoD: поки агент A посеред `deep` (мок повільний), `GET /health` і агент B
   далі відповідають.*
6. **HTTP-помічники.** `GET /agents` (id + статус), `GET /agent/{id}/history?limit=N` зі стору. *DoD:
   свіжий клієнт рендерить недавній скрол при attach.*
7. **Другий агент — Pashu (§12).** Створити мінімальний `state/pashu/` (власні `canon.md` + потреби /
   настрій / промпти) і зареєструвати `AgentRuntime("pashu")` у хості на старті, поруч з Агнікою. Обидва
   агенти тікають одночасно на окремих потоках з ізольованими `.kiln/{id}/` + `state/{id}/`; Pashu
   отримує вужче поле permission-scope (енфорсмент у v1.3). *DoD: хост крутить Агніку + Pashu одночасно;
   клієнт під'єднується до `ws://…/agent/pashu` незалежно; хід в одного агента не чіпає потреби/стор
   іншого.*
8. **Remote TUI-клієнт.** Режим `--remote ws://…/agent/{id}` для Textual-застосунку (обрати Агніку або
   Pashu): `WsBridge` (або пара `Channel`/`Output` поверх WS), що живить наявний `_render`; `render.py`
   перевикористати без змін. *DoD: TUI, під'єднаний через WS до будь-якого агента, тримає повний хід і
   показує панель статусу/потреб, ідентично локальному режиму.*
9. **Доки + контракти.** Оновити `ARCHITECTURE.md` (підняти заплановані пункти про
   сервер/протокол-подій до «поточних»), закріпити протокол подій контрактним тестом. *DoD:
   ARCHITECTURE відповідає поставленому серверу; контрактний тест протоколу зелений.*

**Критичний шлях:** 1 → 2 → 3 → 4 → 7 → 8 (5/6 поруч). **Зусилля:** ~M кожен (протокол, другий агент і
remote-клієнт — основна маса; рушій не чіпаємо). **Про модель:** кожен тест — проти `MockBrain`, **нуль
платних викликів**.

## 11. Ризики та рішення

- **Потік vs async-цикл.** v1.1 свідомо лишає `run()` на потоці (перевірена форма TUI), а не переписує
  на async. Переписування на async/FSM — це **v1.2** і може прийти без зміни протоколу. *Рішення:
  потік-на-агента для v1.1.*
- **Один store, багато писарів.** Лише власний потік агента пише його store; клієнти ніколи не пишуть.
  Мульти-агент використовує **окремі** поагентні стори, тож міжагентної конкуренції нема.
- **Інваріант echo-free.** `ServerOutput.user()` має лишатись no-op, інакше два клієнти подвоять рендер
  вводу. Це контрактний тест.
- **Backpressure.** Повільний/мертвий клієнт не повинен блокувати хаб чи потік рушія; broadcast — best-
  effort на з'єднання (застряглий сокет — drop-and-disconnect), рушій ніколи не чекає клієнта.

## 12. Другий агент: **Pashu** (у межах v1.1)

v1.1 хостить **двох** агентів, а не одного: **Агніку** (`agent_id: "agnika"`, дім / підвищені права) і
**Pashu** (`agent_id: "pashu"`, перший компаньйон). Хостинг *справжнього* другого агента — а не лише
`agent_id`-масштабованого API — це **частина DoD цієї версії**: доказ, що хост — це справжній мульти-
агентний хаб. І **розробка** Pashu, і **під'єднання** до нього входять у v1.1.

**Що для цього треба — і чого не треба:**

- **Нуль змін рушія.** Pashu крутить *той самий* `engine.run()` на *власному* потоці; розум — ідентичний
  код. Різняться лише **дані**. Саме це й дає `agent_id`-масштабування з §8.
- **Розробка (дані Pashu).** Власні `agent_id`-масштабовані шляхи: `state/pashu/` з **власними** `canon.md`
  (персона Pashu), `needs.json` (незалежні рівні), `needs_model.yaml`, `mood.json`, `prompts.md` та
  `.kiln/pashu/{store.json, usage-ledger.jsonl}`. v1.1 постачає **мінімальний канон Pashu**, щоб другий
  агент реально працював (повну персону можна поглиблювати згодом); Агніка і Pashu ніколи не ділять стан.
- **Під'єднання (шина + маршрут Pashu).** Другий `AgentRuntime("pashu")` працює поруч з
  `AgentRuntime("agnika")` (хост — це просто `dict`); `ws://…/agent/pashu` віддає власний broadcast-хаб
  Pashu. Клієнт під'єднується до Агніки **або** Pashu; обидва тікають одночасно, і кілька клієнтів на
  Pashu бачать сесію Pashu так само, як для Агніки.
- **Вужчий permission scope.** **Агніка = дім / підвищені права**; **Pashu = компаньйон з вужчим
  scope**. Поле scope задається на агента у v1.1; **енфорсмент** приходить з інструментами у **v1.3** —
  тож вужчий scope Pashu *кусає* лише тоді.

**Поза межами тут (v2):** операторський **UI керування** для додавання / старту / стопу / інспекції
агентів з панелі (§2.2 у роадмапі). У v1.1 Pashu реєструється в **конфізі** (другий `agent_id` + його
файли `state/pashu/`, обидва стартують на завантаженні сервера); v2 робить це керованим з UI.
