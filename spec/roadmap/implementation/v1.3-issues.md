# v1.3 — GitHub Issues

Issues for phase **v1.3 — FSM core (explicit, table-driven)** (version **v1 — Engine (the tick-server &
hub foundation)**), derived from the per-phase Implementation tasks in [ROADMAP.md](../../ROADMAP.md)
(§v1.3) and the concept in [spec/features/fsm.md](../../features/fsm.md), against the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md) (§The tick loop, §Contracts, §Status event, §Components,
§Output seam). This file is scoped to a single phase; IDs continue from the previous phase (KILN-060 →
**KILN-061…066**).

v1.3 turns `run()`'s implicit `if/elif` tick loop into an **explicit, table-driven state machine** over
a unified **event queue**, with the built-in actions registered as **tools** — the foundation the
declarative FSM (1.7), simulation (1.8), and non-blocking execution (1.9) build on. It is
**behaviour-preserving**: Agnika stays byte-for-byte and the whole v1.2 suite is the behavioural pin.
The static gates (the model, the queue, the action registry) are pure and testable; the risk is
concentrated in the one `run()` rewire.

## v1.3 — FSM core (explicit, table-driven)

### KILN-061 — State + event kinds + transition table + `advance`

**Description:**
The gate: the **static FSM model** in a new module (e.g. `kiln/fsm.py`), touching no runtime yet. A
`State` enum, the `Event` kind vocabulary, the transition **table as data**, and a pure `advance`. The
default table **encodes v1.2's exact behaviour**, so nothing downstream changes what the agent does.

**What needs to be done:**
- A `State` enum: `idle` / `thinking` / `responding` / `cooling` / `resting`.
- The `Event` type + kind vocabulary: `user.message`, `command`, `self_trigger:<need>`, `tick`,
  `rotate.request`; plus **reserved** (defined, unused) `peer.message` / `room.message` / `tool.result`.
- The **default transition table** as data — `(state, event, guard) → (action, next_state)` — encoding
  today's priority (`input > self-trigger > idle`) and the rest-gate hysteresis (enter at
  `rest >= threshold`, wake at `rest <= REST_WAKE`). Guards are **Python predicates** over needs/flags
  (the YAML grammar is 1.7); actions are **names** the registry (KILN-063) will resolve.
- A pure `advance(state, event, ctx) -> (action, next_state)` that looks up the table; `ctx` exposes the
  agent's needs/flags for the guards.

**Dependencies:** None (gate)

**Expected result:**
`advance()` maps every `(state, event)` to the v1.2 action + next state, as data — testable in isolation
with no engine wired up.

**Acceptance criteria:**
- [ ] **Unit test:** `advance` covers every transition/guard — e.g. `idle + user.message → (respond,
  responding)`; `idle + tick [rest ≥ thr] → (enter_rest, resting)`; `resting + tick [rest ≤ wake] →
  (wake, idle)`; a self-trigger crossing → `(reach_out|think, responding|thinking)`.
- [ ] The table names **only** actions the registry (KILN-063) will provide, and only defined states.
- [ ] Pure / no I/O, no `run()` change; runs against `MockBrain` — no paid calls.
- [ ] Ties to DoD: the FSM's states + transitions exist as an inspectable, unit-tested table.

### KILN-062 — Event queue + producers (fold inbox + rotate_results)

**Description:**
The runtime event side: one queue **drained one event per tick** in priority order, fed by **producers**
that turn today's sources into `Event`s — folding the `ServerChannel` inbox and the `rotate_results`
queue into the single queue. Touches `engine.py` (added alongside, not yet driving the loop).

**What needs to be done:**
- An event **queue** (per run) drained **one event per tick** (preserving today's one-action-per-tick
  cadence), by the priority the table expects (`input > self_trigger > tick`).
- **Producers** wrapping today's sources: `channel.poll()` → `user.message` / `command`;
  `select_self_trigger` / `select_thought_trigger` → a `self_trigger:<need>` event **when** a crossing
  fires this tick (hysteresis/cooldown unchanged); the auto-rotate timer / `/rotate` → `rotate.request`;
  a `tick` event each tick. Fold the inbox + `rotate_results` into this one queue.
- Keep the producers thin — they emit events, they don't decide the action (the table does).

**Dependencies:** KILN-061 (the `Event` type/kinds)

**Expected result:**
Each tick produces the right events, and draining yields the **same single event** the current `if/elif`
would act on.

**Acceptance criteria:**
- [ ] **Unit test:** producers emit the correct events for given state/input (input present → a
  `user.message`; a connection crossing → `self_trigger:connection`; always a `tick`).
- [ ] **Unit test:** the drain order equals today's `input > self-trigger > idle` — input + a
  self-trigger in one tick → **input** is acted on (self-trigger re-evaluated next tick, as today).
- [ ] `MockBrain` — no paid calls.
- [ ] Ties to DoD: the unified event queue exists and reproduces the current per-tick selection.

### KILN-063 — Action-registry seam (built-ins as tools)

**Description:**
The **action-registry seam** the FSM fires through — `action-name → callable` — with the built-in
actions registered as **built-in tools**. This is the exact seam **1.5 Tools** extends with user tools.
Touches `engine.py` (a small registry module/section). Seam → ARCHITECTURE.

**What needs to be done:**
- A registry (`name -> callable`) + a `fire(action, ctx)` that resolves and calls.
- Register the built-ins wrapping today's inline behaviour: `chat` / `deep` (via `respond`),
  `reach_out` (`reach_out_branch` + `respond`), `think` (`_think`), `idle` (`apply_satiation(idle)`),
  `rotate` (the rotation path), `enter_rest` / `cool` (the rest/cooldown transitions).
- Each built-in produces the **same effects** as the current inline call (satiation, output, stats).
- ARCHITECTURE §Contracts: note the **action registry** seam — the FSM fires actions = tools; 1.5
  extends the same registry (scope gates which an agent may fire).

**Dependencies:** KILN-061 (the table names the actions)

**Expected result:**
Firing a built-in by name produces the same effect as today's inline call.

**Acceptance criteria:**
- [ ] **Contract test:** the registry resolves **every** action the table (KILN-061) names; the seam
  shape (`name -> callable`, `fire(action, ctx)`) is pinned in ARCHITECTURE in the same change.
- [ ] **Unit test:** each built-in maps to today's behaviour — e.g. `fire("reach_out", ctx)` runs the
  current reach-out path; `fire("idle", ctx)` applies idle satiation — against `MockBrain`.
- [ ] Ties to DoD: the built-in actions are registered tools, ready for 1.5 to extend.

### KILN-064 — Rewire `run()` as a thin FSM driver (behaviour-preserving)

**Description:**
The substantive, risky step: replace `run()`'s `if/elif` action-selection with the **FSM driver** over
the queue (062) + table/`advance` (061) + registry (063). Everything else — drift, satiation,
persistence, rotation, the rest-gate, the model call (still blocking) — is **untouched**. Agnika stays
**byte-for-byte**; the whole v1.2 suite is the pin. Touches `engine.py` (the loop).

**What needs to be done:**
- Per tick: gather events (062) → enqueue → drain one → `advance(state, event, ctx)` (061) → `fire` the
  action via the registry (063) → set the next state → emit `status`.
- Leave `drift` / `apply_satiation` / real-time persistence / rotation / the rest-gate exactly as-is;
  the deep call still **blocks** the agent thread (non-blocking is 1.9).
- Keep the status snapshot emitting the same states (except `cooling`, which lands in KILN-065).
- ARCHITECTURE §The tick loop: promote "pick one action, priority input > self-trigger > idle" to "the
  loop is an FSM over a transition table; the default table encodes that priority".

**Dependencies:** KILN-062, KILN-063

**Expected result:**
The loop is an FSM driven by the queued table; Agnika is byte-for-byte and every existing test passes.

**Acceptance criteria:**
- [ ] **Integration test (MockBrain):** a scripted `user.message` drives `idle → responding → idle` and
  produces the **same reply + satiation + stats** as today; a self-trigger tick drives the reach-out
  path; an idle tick rests — all matching v1.2.
- [ ] **Back-compat:** the **entire existing suite passes unchanged** (Agnika byte-for-byte) — the
  behavioural pin.
- [ ] ARCHITECTURE §The tick loop matches the shipped FSM (planned → current), in this change.
- [ ] Ties to DoD: `run()` is a thin FSM driver over the queued transition table; no behaviour change.

### KILN-065 — `cooling` as a real state

**Description:**
The one **additive** change: surface `cooling` as a real post-turn state (today the per-need cooldowns
in `TriggerBook.cooldown` are tracked but never a status). After a turn the FSM enters `cooling`;
cooldowns tick down; it returns to `idle`. It appears as the snapshot's `status`. Touches the fsm table
+ `engine.py` + the status snapshot. Seam → ARCHITECTURE + contract test.

**What needs to be done:**
- Add the transitions: a turn → `cooling`; `cooling + tick` → `idle` once cooldowns clear.
- The status snapshot reports `status: "cooling"` while in it (the TUI already renders the `status`
  string — no client change needed).
- ARCHITECTURE §Status event / §The tick loop: add `cooling` to the state set.

**Dependencies:** KILN-064

**Expected result:**
After a reply the agent is briefly `cooling`, then `idle` — visible via `/status` and the snapshot.

**Acceptance criteria:**
- [ ] **Integration test (MockBrain):** a turn leaves the agent in `cooling` for the cooldown window,
  then `idle`; the snapshot `status == "cooling"` right after a turn.
- [ ] **Contract test:** the status-snapshot state set now includes `cooling`, pinned in ARCHITECTURE in
  the same change (the snapshot key set is unchanged; the `status` value gains `cooling`).
- [ ] Ties to DoD: `cooling` is a real, observable state.

### KILN-066 — Transition tracing + FSM contract + ARCHITECTURE

**Description:**
Close the phase: emit a structured **trace** of every `state → event → guard → action → state` (the log
**1.8 simulation** will consume), and pin the FSM as a stable contract. Touches the fsm module +
`engine.py` + tests + `spec/ARCHITECTURE.md`. Seam → ARCHITECTURE + contract test.

**What needs to be done:**
- A structured transition **trace**: each transition emits `{tick, state, event, guard?, action,
  next_state, needs}` through a trace sink (a callback / log the harness can capture) — off by default,
  cheap when on, no behaviour effect.
- Pin the **FSM contract**: the `advance` table shape + the (unchanged) WS **event protocol**; a
  contract test that the default table's transitions match v1.2 and the server emits the same events.
- ARCHITECTURE §Contracts: add the FSM seam (states, event kinds, the transition table, `advance`, the
  trace record) as a stable contract.

**Dependencies:** KILN-064 (and the KILN-065 state set)

**Expected result:**
Every transition is traceable; the FSM is a pinned contract; ARCHITECTURE matches the shipped machine.

**Acceptance criteria:**
- [ ] **Unit test:** a run over N ticks produces a trace of the expected transitions (shape + order);
  tracing off = no records, on = one per transition.
- [ ] **Contract test:** the `advance` table + the WS event protocol are pinned; the v1.1 event-protocol
  test stays green (the server emits the same events).
- [ ] ARCHITECTURE §Contracts / §The tick loop match the shipped FSM.
- [ ] Ties to DoD: every transition is traced; the FSM contract is stable for 1.7/1.8 to build on.

## v1.3 scope notes

**Total effort:** ~3–4 weeks (M + M + S + L + S + M). The `run()` rewire (KILN-064, L) is the bulk and
the risk; the three gates (061/062/063) are pure and de-risk it by landing the model, queue, and
registry independently first.
**Critical path:** KILN-061 → KILN-064 → KILN-066 (KILN-062 + KILN-063 run in parallel after 061 and
feed 064; KILN-065 runs alongside 066).
**Phase DoD (ROADMAP §v1.3):** the loop is an FSM over a queued transition table; `advance(state, event)`
is unit-tested; the default table reproduces v1.2 behaviour (Agnika byte-for-byte, all tests green);
`cooling` is a real state; every transition is traced; the server emits the same events.
**Contracts pinned this phase:**
- **Action registry** — `name -> callable`; the FSM fires actions = tools; 1.5 extends it (KILN-063).
- **The tick loop is an FSM** — `run()` drives a queued transition table; ARCHITECTURE §The tick loop
  promoted (KILN-064).
- **Status states** — `cooling` added to the snapshot's `status` set (KILN-065).
- **FSM contract + trace** — the `advance` table + trace record + the unchanged event protocol
  (KILN-066).
**Scope guard:** the **YAML** guard grammar + per-agent `fsm.yaml` loader are **1.7**; simulation /
analytics **1.8**; **non-blocking** execution (the model call still blocks) **1.9**; `peer.message` /
`room.message` / `tool.result` are **reserved** but unused until **1.6 / 1.11 / 1.5**. Guards stay Python
predicates this phase.
**Model note:** the model runs behind the brain seam; **no paid APIs** — `MockBrain` returns canned
replies for the unit + integration tests; the whole existing suite is the behavioural pin.
