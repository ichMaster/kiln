# v0.3 — GitHub Issues

Issues for phase **v0.3 — Implement TUI** (version **v0 — Prototype & TUI**),
derived from the per-phase Tasks in [ROADMAP.md](../../ROADMAP.md) (§v0.3) and the
contracts in [ARCHITECTURE.md](../../ARCHITECTURE.md) (Overview, Components —
Channels/Output/Clients, Contracts, Repository layout). This file is scoped to a
single phase; IDs continue from the previous phase (KILN-006 → **KILN-007…011**).

Phase v0.3 puts a real **Textual** terminal UI in front of the engine. The payoff of
v0.2 is that the core already exposes the seams this phase needs — `run(output=…,
channel=…)`, the `Output` port, and the `Channel` `poll()` — so v0.3 plugs a TUI into
them through an **echo-free bridge bus** and **touches no engine core code**. The
bridge is also the shared bus for the later web/server clients (v1.1/3.1).

## v0.3 — Implement TUI

### KILN-007 — `tui/` package & echo-free bridge bus

**Description:**
The gate. Create the `tui/` client package and the **echo-free bridge** — a
thread-safe inbox/outbox bus that decouples the engine's tick loop from the Textual
UI thread. The render-event protocol on the outbox mirrors the v0.2 `Output` seam
(`user`/`agent`/`usage`/`notice`). New `tui/` dir (per ARCHITECTURE, a new dir as the
version begins); the client holds **no agent logic** and the engine core is untouched.
Seam → ships its ARCHITECTURE update + contract test here.

**What needs to be done:**
- Create the `tui/` package (`tui/__init__.py`, `tui/bridge.py`); no agent logic.
- `Bridge`: a thread-safe **outbox** (engine→UI render events) and **inbox**
  (UI→engine typed lines), e.g. `queue.Queue`; both drained non-blocking so neither
  the tick loop nor the UI stalls.
- Define the render-event shape carried on the outbox, mirroring the `Output` methods
  (`user`/`agent`/`usage`/`notice`) so the v0.2 seam maps onto the bus 1:1.
- **Echo-free:** a user's typed line goes only into the inbox (engine input); the
  engine echoes nothing of it — only its own replies/usage/notices flow to the outbox.
- Update [ARCHITECTURE.md](../../ARCHITECTURE.md) Components (a `tui/` bridge bus) +
  Contracts (the bus event protocol, foreshadowing the v1.1/1.2 server events).

**Dependencies:** None (gate; builds on the already-shipped v0.2 `Output`/`Channel` seams).

**Expected result:**
A thread-safe `Bridge` with inbox/outbox and a shared render-event protocol,
importable as the `tui/` package; no engine changes.

**Acceptance criteria:**
- [ ] `tui/` package imports; `Bridge` exposes put + non-blocking get for both inbox
      and outbox; an idle get returns "empty" (won't stall the loop).
- [ ] **Contract test:** bus round-trip — render events put by the engine side are
      drained by the UI side; a typed line flows UI→engine; **nothing the user typed
      is echoed on the outbox** (echo-free).
- [ ] **Unit test:** non-blocking drain returns empty/None when idle.
- [ ] ARCHITECTURE updated with the bridge bus (ties to DoD: the shared echo-free bus).

### KILN-008 — `TuiOutput` sink — Output seam over the outbox

**Description:**
Implement the v0.2 `Output` protocol as `TuiOutput`, translating
`user`/`agent`/`usage`/`notice` into render events on the bridge **outbox** instead
of `print`. `tui/output.py`. This is the mirror of `ConsoleOutput`, but for the bus.

**What needs to be done:**
- `TuiOutput(bridge)`: each `Output` method pushes a render event onto `bridge.outbox`.
- Build the `usage` event from the same token fields `print_tech` uses (so the UI can
  render the tech line); carry the `is_self`/`lead` hints on the `agent` event.
- Keep `runtime_checkable` `Output` conformance (so `isinstance(TuiOutput(...), Output)`).

**Dependencies:** KILN-007.

**Expected result:**
Passing `TuiOutput` to `run(output=…)` makes the engine's replies/usage/notices flow
onto the bridge outbox with zero engine changes.

**Acceptance criteria:**
- [ ] `TuiOutput` satisfies the `Output` protocol; a turn's `agent` reply + `usage`
      land as outbox events.
- [ ] **Contract test:** drive `run()` with `MockBrain` + `TuiOutput`; assert the
      outbox receives the reply + usage events — **zero paid calls**.
- [ ] Ties to DoD: the engine writes only its own replies to the bus (echo-free).

### KILN-009 — `TuiChannel` — inbox-backed input `poll()`

**Description:**
A `Channel` (`poll()`) backed by the bridge **inbox** — the UI mirror of
`StdinChannel`, so the tick loop reads UI-typed lines off the bus without stalling.
`tui/channel.py`.

**What needs to be done:**
- `TuiChannel(bridge)`: `poll()` does a non-blocking get from `bridge.inbox` (returns
  `None` when empty), matching `StdinChannel`'s contract.
- Ensure the tick loop never blocks waiting on input (mirror the daemon/queue pattern).

**Dependencies:** KILN-007.

**Expected result:**
Passing `TuiChannel` to `run(channel=…)` feeds UI-typed lines into the tick loop.

**Acceptance criteria:**
- [ ] `TuiChannel.poll()` returns a queued line once, then `None` when the inbox is empty.
- [ ] **Contract test:** a line put on the inbox is consumed by `poll()` and drives a
      `respond()` turn against `MockBrain` (no paid call).
- [ ] Ties to DoD: chat in the TUI (typed lines reach the engine).

### KILN-010 — Route slash-command output through the Output seam

**Description:**
Generalize `handle_command` to emit through the v0.2 `Output` port instead of `print`,
so any client (TUI now, web later) captures command results — finishing the work
KILN-006 deferred. Touches `commands.py` + `engine.run()`. Seam change (the command
surface) → ships its ARCHITECTURE note + contract test. Independent of the TUI gate
(it only needs the existing `Output` seam).

**What needs to be done:**
- Pass the `output` port into `handle_command`; replace its `print(...)` calls
  (`/status`, `/needs`, `/memory`, `/history`, `/help`, `/clear`, unknown) with
  `output.notice(...)`.
- `run()` passes `output` to `handle_command`.
- Update [ARCHITECTURE.md](../../ARCHITECTURE.md) to note command output flows through
  the `Output` seam (the core/commands no longer `print`).

**Dependencies:** None (uses the v0.2 `Output` seam; parallel to the gate).

**Expected result:**
Slash-command results render through the `Output` port — identical on the console
today (`ConsoleOutput.notice`), capturable by the TUI tomorrow; `commands.py` no
longer prints.

**Acceptance criteria:**
- [ ] `commands.py` contains no `print(`; all command output goes via `output.notice`.
- [ ] **Contract test:** a captured `Output` receives `/status` and `/needs` results;
      the `handle_command` signature is pinned.
- [ ] **Unit test:** dry-run smoke output is unchanged on the console (mock brain).
- [ ] Ties to DoD: no interleaving — the UI owns all rendering.

### KILN-011 — Textual app + launcher + concurrent tick loop

**Description:**
The Textual app (port `lumi/tui/app.py`): a fixed input line at the bottom + a
scrollable reply log above, wired to the bridge; the engine `run()` loop runs on a
**background thread** so it keeps ticking and can self-trigger while the UI renders,
with model calls off the UI thread. Adds the launcher (`kiln --tui`). `tui/app.py` +
the `__main__` launcher. Largest issue in the phase.

**What needs to be done:**
- Textual app: a scrollable log that drains `bridge.outbox` and renders
  `user`/`agent`/`usage`/`notice` with the `you`/`Agnika`/tech colors as Textual
  styles; a fixed bottom input that submits typed lines to `bridge.inbox`.
- Start `run()` on a background thread (TUI mode, `ticks=None`) with `TuiChannel` +
  `TuiOutput`; the loop never blocks the UI and model calls happen off the UI thread.
- Launcher: `kiln --tui` (flag) or a `tui` console entry; the plain console mode is
  preserved. Add `textual` to `pyproject.toml` (a `tui` optional extra).
- Carry over the `you`/`Agnika`/tech colors.

**Dependencies:** KILN-007, KILN-008, KILN-009, KILN-010.

**Expected result:**
A working Textual TUI chat with no input/output interleaving; the agent keeps ticking
and can self-trigger while the UI is open.

**Acceptance criteria:**
- [ ] `kiln --tui` launches the app; typing a line yields an `Agnika` reply in the
      log; **no input/output interleaving**.
- [ ] The tick loop runs concurrently — a self-trigger fires into the log while idle
      (scripted/demo), and the UI stays responsive during a (mock) model call.
- [ ] **Integration test:** a Textual pilot drives one turn against `MockBrain` (zero
      paid calls) if practical; otherwise an integration test of the
      app↔bridge↔engine wiring on the mock brain. CI stays green.
- [ ] Ties to DoD: chat in a Textual TUI, echo-free, the loop keeps running.

## v0.3 scope notes

**Total effort:** ~3–4 weeks (1 × M gate + 3 × S + 1 × L), roughly 14–20 dev-days.
**Critical path:** KILN-007 → KILN-008/009 → KILN-011.
**Phase DoD (ROADMAP §v0.3):** chat in a Textual TUI with no input/output
interleaving; the engine writes only its own replies to the bus (echo-free); the tick
loop keeps running (self-triggers still fire) while the UI is open.
**Contracts pinned this phase:** the **bridge bus** (inbox/outbox render-event
protocol, echo-free — KILN-007) + its contract test; `TuiOutput` against the `Output`

**command surface** emitting via `Output` (KILN-010) + its contract test.
**Core untouched:** v0.2's seams mean the engine `run()`/`respond()` need **no
changes** — v0.3 is all client/adapter code behind the existing `output`/`channel`
parameters (the one exception, KILN-010, generalizes `handle_command` to use the same
`Output` seam, not the core loop).
**Model note:** the model runs behind the brain seam; **no paid APIs** — a mock brain
returns canned replies for unit + integration tests (incl. the Textual pilot).
